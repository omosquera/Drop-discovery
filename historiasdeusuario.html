Insumo para checkpoint PO + Tech Lead + Designer — Novedades y casos SAC[cite: 6]

Cómo usar este documento[cite: 6]

Este documento es el insumo de entrada para el primer checkpoint conjunto entre PO, Tech Lead y Designer[cite: 6]. No es un spec cerrado: cada historia trae criterios de aceptación en formato Gherkin (Dado / Cuando / Entonces), y varios criterios están marcados como preguntas abiertas — decisiones que el diseño no puede resolver solo y que requieren negocio (PO) y factibilidad (Tech Lead)[cite: 6].

Cubre las tres features del cuadrante "hacer primero" que sostienen el flujo crítico del Agente SAC: bandeja priorizada (F1), vista de caso unificada (F2), y evidencia obligatoria al resolver (F4)[cite: 6].

Historia 1 — Bandeja priorizada por urgencia F1[cite: 6]

Como agente SAC, quiero que mi bandeja de casos esté ordenada automáticamente por tiempo restante de SLA, para atender primero los casos con mayor riesgo de incumplimiento sin depender de mi memoria[cite: 6].
Dado que tengo varios casos abiertos con distintos tiempos restantes de SLA
Cuando abro mi bandeja de casos
Entonces se muestran ordenados de menor a mayor tiempo restante, con el más urgente primero[cite: 6]
Dado un caso con menos de 2 horas de SLA restante
Cuando veo la bandeja
Entonces el caso se resalta visualmente como urgente[cite: 6]
Dado que dos casos tienen el mismo tiempo restante de SLA
Cuando se ordenan en la bandeja
Entonces se aplica un criterio de desempate acordado con dev (ej. antigüedad del caso)[cite: 6]
❓ Pregunta abierta para el checkpoint[cite: 6]
¿Cuál es el criterio de desempate correcto cuando dos casos tienen el mismo tiempo restante?[cite: 6] El diseño identifica que se necesita uno; el negocio (PO) y la factibilidad de datos (Tech Lead) definen cuál[cite: 6].

Historia 2 — Vista de caso unificada F2[cite: 6]

Como agente SAC, quiero ver en una sola pantalla la urgencia, el contexto del pedido, la evidencia y el historial del caso, para no tener que salir a Excel o WhatsApp mientras resuelvo una novedad[cite: 6].
Dado que abro un caso desde la bandeja
Cuando se carga la vista de caso
Entonces veo en la misma pantalla: estado + SLA restante, datos del pedido/vendedor/transportadora, evidencia adjunta e historial[cite: 6]
Dado que el caso tiene evidencia adjunta previamente
Cuando abro el caso
Entonces puedo verla sin navegar a otro módulo[cite: 6]
Dado que el caso no tiene ninguna acción registrada aún
Cuando abro el caso
Entonces la zona de historial muestra un estado vacío explícito, no un espacio en blanco ambiguo[cite: 6]
❓ Pregunta abierta para el checkpoint[cite: 6]
¿Qué campos del "contexto del pedido" ya viven en un mismo servicio/API hoy, y cuáles requieren llamadas a sistemas distintos (pedido, transportadora, vendedor)?[cite: 6] Define si la vista se puede construir en un solo sprint o necesita orquestación adicional[cite: 6].

Historia 3 — Evidencia obligatoria al resolver F4[cite: 6]

Como agente SAC, quiero que el sistema me exija adjuntar evidencia antes de cerrar una novedad, para reducir la tasa de reapertura por falta de respaldo[cite: 6].
Dado que estoy resolviendo una novedad
Cuando intento guardar la solución sin adjuntar evidencia
Entonces el sistema bloquea el guardado y muestra un mensaje indicando que se requiere evidencia[cite: 6]
Dado que adjunto una evidencia válida (foto, captura, comprobante)
Cuando guardo la solución
Entonces el caso se actualiza y la evidencia queda visible en el historial[cite: 6]
Dado que el tipo de novedad es "cliente rehúsa pagar o recibir"
Cuando documento el motivo
Entonces el sistema exige elegir una causa de una lista estructurada, no texto libre[cite: 6]
❓ Pregunta abierta para el checkpoint[cite: 6]
¿Qué cuenta como "evidencia válida"?[cite: 6] ¿Hay un tamaño/formato de archivo que el backend ya soporta, o hay que definirlo desde cero?[cite: 6] Sin esta definición compartida, el criterio de aceptación no es verificable[cite: 6].

Por qué estas preguntas van en este documento y no se resuelven aquí[cite: 6]

Cada historia tiene al menos un criterio que el diseño no puede cerrar solo[cite: 6]. Esa es la prueba de que el checkpoint PO + Tech Lead + Designer no es un formalismo — es el punto donde intención de negocio, factibilidad técnica y lógica de interacción se encuentran antes de que cualquiera de los tres construya algo por su cuenta[cite: 6].

Salida esperada del checkpoint: cada pregunta abierta resuelta y anotada directamente en este documento, convirtiendo cada historia en un criterio de aceptación cerrado y verificable — recién ahí queda lista para pasar a diseño de detalle y desarrollo[cite: 6].
